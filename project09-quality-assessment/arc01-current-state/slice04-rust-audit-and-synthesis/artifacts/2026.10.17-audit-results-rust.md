## Concurrency and runtime safety

### RUST-001 — High — Backend panic leaves the REPL permanently waiting

**Location:** `crates/xrepl-core/src/repl.rs:66–81,95–99,117–126,137–145`;
`crates/xrepl-core/src/input.rs:43–59`; public completion promise
`crates/xrepl-core/src/repl.rs:47–57`.
**Scale:** logical unit / public library / executable lifecycle.

**What's wrong:** The core waits only for the next event and does not monitor
the backend JoinHandle while running. If `Backend::handle` panics, its event
sender drops, but the input thread still owns another sender and waits for a
prompt pulse that only the now-missing BackendIdle event would trigger.

**Why it matters:** The event channel stays open, `event_rx.recv()` never
completes, and input cannot deliver another line or EOF because the editor is
parked on `prompts.recv()`. The function therefore never reaches its documented
peer-failure teardown or awaits the already-failed backend task. This is a
failure-isolation defect in the current public Backend seam; it does not require
the deferred BEAM backend or interrupt feature. High reflects the permanent loss
of interactive progress when an installed backend fails; the bundled small
adventure was not observed to panic on valid user commands.

**Evidence:** The retained neutral public-API harness runs the real local
`xrepl_core::run`, not a model of its channels. Its normal hello→quit control
returns Ok and exit0; Ctrl-D control also returns Ok and exit0. The panic case
prints `PROBE_BACKEND_PANIC` from the real Tokio backend task, then fails to
return for the five-second bound; the harness terminates only its own child.
See [final probe log](rust-probes/pty-final.log). This matches the source's
closed backend / live input sender ownership cycle exactly.

**Fix direction:** Monitor task completion alongside event reception, observe
JoinError and propagate a typed failure after terminating the remaining peer.
Release the parked input by closing its pulse sender in this demonstrated
state. A general supervisor must also account explicitly for an editor currently
inside blocking read_line; do not assume dropping the pulse sender interrupts
that call. Add real-core behavioral regression coverage with normal/EOF controls
and a bounded failing-backend oracle; protect the existing turn-order contract.
Relevant loaded guidance: CA-01, CA-32/33/37, AP-33; refinement also checked EH-01,
EH-04 and PS-03 against the existing public peer-failure completion promise.

## Error handling

### RUST-002 — Medium — Terminal failure is returned as successful completion

**Location:** `crates/xrepl-core/src/input.rs:44–51`;
`crates/xrepl-core/src/repl.rs:109–127`;
`crates/xrepl-core/src/error.rs:11–14`; binary
`crates/xrepl/src/main.rs:13–16`.
**Scale:** public API / executable exit contract.

**What's wrong:** An unrecoverable line-editor error becomes InputError, gets
printed as a Meta frame, and then the core returns Ok. The existing Io error
variant is never used on this path, and the diagnostic renderer writes to stdout.

**Why it matters:** A caller cannot distinguish a failed terminal from normal
quit/EOF. The binary forwards this Ok and exits successfully, so launching the
program with unusable input can appear successful even though no prompt was
usable. The run documentation explicitly calls it currently infallible; that
documents the implementation choice but does not provide failure observability.
Medium reflects reporting/recovery reliability rather than state corruption.

**Evidence:** In this macOS audit environment a neutral process with stdin
`/dev/null`, captured stdout/stderr, emits stdout `input error: Operation not
permitted (os error 1)` and stderr `PROBE_RETURNED:Ok(())`, exit0. The probe
records the result from `run`; its own main does not invent that result. Normal
PTY Ctrl-D returns Ok without the input-error diagnostic, providing a separate
successful EOF control. See [final probe log](rust-probes/pty-final.log).

**Fix direction:** Preserve the input I/O error as structured event data,
complete teardown, and return Err(Io). Route the failure diagnostic to stderr at
the application edge; reserve Ok for deliberate quit/EOF. Validate successful
quit, Ctrl-D, and failed terminal as distinct outcomes with the same real core.
Relevant loaded guidance: AP-33, CLI-16/20/55; refinement also checked EH-01/04/14/26
and PS-03. A Result-returning main is valid; the defect is the erroneous Ok from
the library, not the binary's return-type style. Sofie reports an independent
replay with errno6 rather than this author's errno1: the stable observed failure
is an input-error diagnostic followed by Ok, not a particular OS errno.

## Testing and automation

### RUST-003 — Medium — Rust lifecycle has no behavioral gate in CI

**Location:** `.github/workflows/cicd.yml:14–78`;
`crates/xrepl-core/src/lib.rs:25–41`;
`crates/xrepl-adventure/src/lib.rs:249–309`;
`mk/rust.mk:77–90`.
**Scale:** crate / executable / whole Rust codebase / polyglot CI.

**What's wrong:** The sole CI workflow runs only BEAM build/test jobs. The Rust
workspace's seven unit tests all call the adventure directly; the sole core
doctest is compile-only (`no_run`), and core/binary have zero unit tests.

**Why it matters:** The selected PoC is infrastructure, yet its event loop,
input-thread completion, peer panic and executable exits have no automated
behavioral protection. Passing the current suite does not exercise the public
coordination path that RUST-001 and RUST-002 break; without Rust CI even that
limited build/lint coverage is not enforced on changes. Zero tests alone is
not proof of a product bug; the concrete probes above show the missing boundary.

**Evidence:** Independent `cargo test --offline --locked --workspace
--all-features` exit0: adventure7; core0; binary0; compile-only doctest1.
Independent Clippy with all-targets exit0. Workflow read in full and tracked
`.github` population inspected; no Rust job or command exists.

**Fix direction:** Add a Rust CI gate that installs the intended toolchain and
runs locked workspace test, all-target/all-feature Clippy and fmt check. Add a
deterministic input seam or isolated PTY regressions around real `run` for normal
turn/quit, EOF, input error and failed backend; retain the pure domain tests.
Keep infrastructure proof separate from deferred features and future protocol
acceptance. Guidance: CA-32/33/37; CG-L-01/06, CG-F-01; refinement checked PS-02/21/29,
DC-11 and CG-A-08/09. The no_run doctest is valid compilation coverage; it is not
runtime lifecycle evidence. Test the declared MSRV before accepting compatibility
with 1.85; this assessment did not execute that toolchain.

## Coherence, support boundaries and explicit deferrals

The core/input/backend/renderer split has a consistent event vocabulary and
clear directional ownership. The synchronous Backend contract
(`backend.rs:14–20`) is adequate for this tiny in-memory mock. Its assertion that
a network backend slots behind the same trait should be revisited before that
work: `repl.rs:139` calls it directly on a Tokio worker, with no asynchronous
reply/error or incremental-output contract. This is a future design question,
not an allegation that the explicitly deferred protocol client is incomplete.

Output loss is explicitly best-effort (`render.rs:37–40`); frame stream tags are
distinguished but rendered identically. No reliable-output or stderr-routing
claim is accepted from the type names alone. Decide output error policy before
promising a durable transcript. Dropping/cancelling the public run future and
input-thread panic were traced as related lifecycle risks but not independently
probed here; do not count them as additional reproduced failures.

## Things checked and found clean

1. All Rust files searched for unsafe/transmute/manual Send/Sync; none present.
   Every crate inherits `unsafe_code = forbid` from the workspace.
2. No caller-input parsing unwraps were found. The three private adventure
   expects concern `here` and known rooms; constructor and all fixed exits name
   existing rooms, and public fields cannot violate that invariant.
3. No Rc/RefCell/shared mutex state or lock held across await appears in this
   Rust population. Backend state moves to one owner task; input owns its editor.
4. Both Tokio queues are bounded (event256, command32). The standard pulse queue
   is unbounded in type, but the inspected turn cadence grants one next turn per
   input/end-of-turn; no claim is made that payload bytes are globally capped.
5. Blocking read_line runs on a dedicated std thread, and its blocking_send is
   outside Tokio workers; no unsafe blocking bridge is used.
6. Neutral normal turn→quit and Ctrl-D controls return promptly with Ok, and the
   backend output appears before the next prompt. This negative evidence is
   bounded to these controls, not general lifecycle correctness.
7. All three crates inherit common edition/MSRV/lints; dependencies flow binary→
   adventure/core and adventure→core with no cycle or reverse core dependency.
