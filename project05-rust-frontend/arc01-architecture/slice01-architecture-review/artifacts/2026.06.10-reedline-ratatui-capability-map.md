# reedline + ratatui Capability Map (for the xrepl Rust core)

**Date:** 2026.06.10 · **Purpose:** map the *current* (June 2026) feature sets of
reedline and ratatui against what an xrepl Rust front-end needs, and name the one
hard constraint that shapes the whole architecture: **both libraries want to own
the terminal.** Versions and claims are cited; anything unverified is flagged.

## 2. What reedline gives you (and what it doesn't)

reedline is a *line editor*, not a UI framework. It owns one job — read a line of
input with rich editing — and does it extremely well. Verified present in 0.48.0:

- **Prompts**: left/right, multiline continuation, vi-mode indicator, and a
  **transient prompt** (`with_transient_prompt`) so accepted lines collapse to a
  compact form. Good for a clean REPL scrollback.
- **Completion**: `Completer` trait + four menu styles (`ColumnarMenu`,
  `IdeMenu`, `ListMenu`, `DescriptionMenu`); quick/partial completion. This is
  where xrepl's LFE symbol completion lives.
- **Hinting**: fish-style autosuggest (`DefaultHinter`, `CwdAwareHinter`).
- **Highlighting**: `Highlighter` → `StyledText` — syntax-highlight LFE forms as
  you type.
- **Validation / multiline**: `Validator` (`DefaultValidator` already balances
  brackets/quotes) — this is exactly the "is the s-expression complete yet?"
  check xrepl's `read-multiline` does by hand today.
- **History**: file-backed *and* SQLite-backed (`SqliteBackedHistory`, rich
  metadata: timestamp, cwd, exit status); `History` trait for custom backends.
- **Editing modes**: Emacs, Vi (with text objects since 0.43), experimental
  Helix (0.47/0.48, feature-gated).
- **New since late 2025 and directly useful**: OSC 133/633 semantic prompt
  markers (`with_semantic_markers`, 0.46) so terminals can mark prompt regions;
  **external break signal** (`with_break_signal`, 0.47) to interrupt `read_line`
  from another thread — *this is the hook that lets a BEAM-side event unblock the
  prompt*; `idle_callback` (0.46); fish-style abbreviations (0.48).
- **`ExternalPrinter`** (feature-gated, **documented "Experimental"**): print to
  the screen *above* the prompt from another thread while the line editor is
  active. The closest thing reedline has to async output.

**The wall.** reedline has **no pluggable painter and no render-into-a-buffer
API** — verified by the complete 0.48.0 builder-method list. During `read_line`
it paints directly to the terminal it owns. Its own docs list "concurrent output
stream … while the input prompt is active ('Full duplex' mode)" as a *future*
improvement. So: reedline cannot draw inside a ratatui region, and ratatui cannot
host reedline's editor. They are two terminal owners.

## 3. What ratatui gives you (and the one thing to internalise)

ratatui is an *immediate-mode TUI framework*. You own a render loop; each frame
you draw widgets into a `Buffer` and it diffs to the terminal. Verified in
0.30.1:

- **Backends**: crossterm (default), termion, termwiz — now separate crates after
  the 0.30 split.
- **The split itself** (0.30.0): `ratatui-core` is now a stable base, so
  third-party widgets can depend on it without churning every ratatui release.
  This matters for xrepl: a custom "LFE value inspector" widget can target
  `ratatui-core 0.1.x` and not break on ratatui minor bumps.
- **Inline viewport** (`Terminal::with_options` + `Viewport::Inline`, plus
  `insert_before`): a partial-screen TUI that **coexists with normal scrollback**
  — the REPL keeps its scrollback history and renders a live region below it.
  0.30.1 specifically fixed inline-viewport resize glitches. This is the mode an
  inline REPL wants.
- **Widgets**: Table, Chart (now with `GraphType::Area` fill, 0.30.1), BarChart,
  Sparkline, Canvas (Braille/Quadrant/Sextant/Octant/Custom markers), Gauge,
  List, Tabs, Scrollbar, Calendar, Paragraph, Block (shadows, merged borders),
  Fill.
- **`Terminal::apply_buffer`** (0.30.1): commit a buffer incrementally outside
  `draw` — useful when another system (here: incoming BEAM messages) drives
  partial updates.
- **Images** via `ratatui-image` 11.x: **sixel, kitty, iTerm2, and
  unicode-halfblock** — this is the Reveal-like inline-graphics capability the
  xrepl graphics docs wanted, already solved on the Rust side. xrepl's LFE
  `xrepl-term` graphics work (iTerm2/Kitty/sixel escape generation) is
  *reimplementing in LFE what `ratatui-image` already does in Rust.*
- **Editor widgets** (if you go ratatui-only for input): `ratatui-textarea`
  0.9.1, `edtui` 0.11 (vim-like; used by `nu-explore`), `tui-prompts`.
- **Markdown**: `tui-markdown` 0.3.7 — render doc strings / `(doc …)` output.

**No built-in async render API** (inferred from absence in 0.30.0/0.30.1 release
notes — *flagged as inference, not an explicit project statement*). Async is an
application concern; `apply_buffer` eases composition with an external event
source.

## 4. The hard constraint: two terminal owners

This is the single fact that shapes the architecture. From the Rust users forum
(Aug 2024) and confirmed by reedline's lack of a painter API: **a line editor and
a TUI framework both want to control the screen, so they conflict.** You cannot
naively run a reedline `read_line` and a ratatui `draw` loop over the same
terminal simultaneously.

There are exactly three workable shapes, and nushell itself demonstrates the
first:

**Pattern A — Alternating modes (nushell's `explore`).** reedline owns the prompt
in the normal loop. When the user invokes a rich view (xrepl's "reveal this
value", a data table, an image, a live process dashboard), the app *suspends* the
line editor, takes over with a ratatui app (usually on the alternate screen),
runs it to completion, restores, and returns to the next `read_line`. nushell
ships exactly this: reedline for the REPL, `nu-explore` (ratatui ^0.30 + edtui +
tui-tree-widget) for the pager. *Mechanism details (alt-screen handoff between
`read_line` calls) inferred from the dependency structure — flagged.*

**Pattern B — ratatui owns everything; input is a ratatui widget.** Drop reedline;
build the prompt as a ratatui editor widget (`ratatui-textarea`/`edtui`) inside a
`Viewport::Inline` layout, with `insert_before` for scrollback. You get one
coherent render loop and can show live regions *and* the prompt at once — at the
cost of reimplementing the line-editing niceties reedline gives for free
(completion menus, vi text objects, history search UI).

**Pattern C — reedline owns the line; ratatui never runs concurrently, only
between lines, inline.** A middle road: normal input via reedline; for *output*
that wants structure (a table, a chart), render a ratatui `Buffer` to a string
and `insert_before`-style print it into scrollback as static content, not a live
app. Live/interactive views still require Pattern A's hand-off.

There is **no bridge crate** that fuses the two and **no reedline API to render
inside a ratatui region** — verified, not assumed.

## 5. The BEAM-from-Rust piece

There are two distinct ways for the Rust core to reach the BEAM, and they sit at
different points on the fidelity/complexity curve: speak Erlang *distribution*
(become a node), or speak xrepl's *existing msgpack socket protocol* (stay a
client of a contract). 5.1 covers the distribution route; 5.2 weighs it against
the msgpack protocol you already have.

### 5.1 Distribution: the Rust core as a peer node

For the Rust core to talk to the xrepl BEAM services as a peer node (the
architecture doc's vision), the relevant crates exist and are maintained:

- **`erl_dist` 0.8.0** (sile): EPMD client, full distribution handshake (client
  *and* server side), term channel. Single-maintainer but active.
- **`erl_rpc` 0.4.0** + **`eetf` 0.12.0**: RPC and External Term Format.
- **`erldash`** is working prior art: a terminal Erlang dashboard built from
  `erl_dist ^0.8 + erl_rpc ^0.4 + ratatui ^0.30`. That is *almost exactly* the
  xrepl Rust-core shape — a ratatui TUI speaking distribution to a BEAM node —
  and proves the stack composes.
- **`edp-rs`** (`edp_client` 0.16.0, michaelklishin) is a newer alternative
  targeting OTP 26/27 ("should be compatible with Erlang 28"); its `ets-browser`
  example is a Rust TUI browsing a live node's ETS tables.
- **Dead end to avoid**: Lumen/Firefly (BEAM-on-Rust AOT compiler) was archived
  June 2024. Do not plan on running BEAM bytecode inside Rust.

**Caveat for xrepl specifically:** the mount has **OTP 30.0-rc0**. `erl_dist`'s
handshake implements specific distribution-protocol versions; confirm 0.8.0
negotiates cleanly against OTP 30 before committing (the protocol is stable but
30 is new — *verify against a live node, don't assume*).

### 5.2 Distribution vs. the existing msgpack socket protocol

The thing easy to forget — and the thing that changes the risk calculus — is that
xrepl **already has** a working wire protocol: `xrepl_protocol` (msgpack over a
4-byte-length-framed socket: UDS locally, TCP remotely), with the BEAM dispatcher
on one end and an *already-shipping TypeScript client* on the other. The Rust core
can be one more client of that contract instead of becoming a node. Here is the
honest comparison.

| Axis | msgpack socket protocol (existing) | Erlang distribution (`erl_dist`) |
|------|-----------------------------------|----------------------------------|
| **Exists today?** | Yes — built, framed, with a TS client proving it's polyglot | No — new Rust code + handshake to bring up |
| **Coupling to BEAM internals** | None — depends on a *message contract*, immune to OTP dist-version churn | Tight — pinned to the distribution protocol version; OTP 30-rc0 unverified |
| **Term fidelity** | Lossy: values are formatted to strings server-side today; structured terms need a protocol extension | Native: `eetf` carries real Erlang terms, full fidelity |
| **What it unlocks** | The REPL, sessions, eval, history — everything Phase 3 already does | *Attach to any running node*, `rpc` calls, live system introspection (`erldash`-class) |
| **Security surface** | Small and understood: UDS file-perms locally, token over TCP (audit L-02/L-03/L-06 to fix) | Large: a connected node can run arbitrary code on its peers (`AP-03`); weak cookie; needs TLS dist |
| **Maintenance** | Yours, but small and already written | `erl_dist` is single-maintainer; `edp-rs` is the fallback |
| **Prior art for this exact shape** | The TypeScript client + VSCode extension | `erldash` (erl_dist + erl_rpc + ratatui) |
| **Bring-up risk** | Low — the contract is proven across two languages | Medium — handshake, cookie, OTP-30 negotiation all to verify |

**The pros, plainly.**

*msgpack protocol — pros:* zero new transport to invent; the contract is already
proven polyglot (TS today, Rust next, Emacs/VSCode in the design docs), so the
Rust front-end becomes one more client of an *ecosystem asset* rather than a
bespoke integration; decoupled from BEAM dist-version churn (it'll survive
OTP 30→31→… untouched); the smallest, most-understood security surface; lets you
ship M1 (Rust-core parity with the local REPL) fast and de-risk the whole
inversion before touching anything exotic.

*msgpack protocol — cons:* it's a custom protocol you own and evolve; today it
flattens values to strings before sending (`xrepl-dispatcher`'s `format-value`),
so the live-term-inspection feature (Reveal's whole point) needs a *structured*
term encoding added to the protocol — real work, though an extension, not a
rewrite; and it does **not** give you the "attach to a live foreign node" power
that distribution does.

*distribution — pros:* native term fidelity out of the box (no string-flattening
problem); the Rust core becomes a real cluster participant, which is the *only*
way to get the killer "point xrepl at a running production system and drive it"
capability; `erldash` proves the Rust+ratatui+dist stack composes.

*distribution — cons:* nothing exists yet (all bring-up); tightly coupled to the
distribution protocol version with OTP-30-rc0 unverified; a much larger security
surface (`AP-03` — arbitrary remote code execution between connected nodes, weak
cookie, mandatory TLS for any non-loopback use); a single-maintainer dependency;
and it would mean *not* reusing the protocol investment you've already proven
across two languages.

**The call (consistent with the architecture review §4):** make the **msgpack
protocol the default and the thing M1 builds on** — it's already built, already
polyglot, lowest-risk, and decoupled from dist churn. Treat **distribution as a
*second* transport behind the same `Transport` trait**, added at M4 specifically
to power "attach to a live node," gated behind explicit opt-in + TLS, and only
after the OTP-30 handshake is verified against a real node. The one piece of
forward work the msgpack path needs regardless is a **structured-term encoding**
(negotiated via the `describe` op) so live inspection isn't bottlenecked by
today's string-flattening — schedule that with M2's ratatui views, not before.

**The encoding to use is EETF-in-msgpack**, and it dissolves what first looks
like a dilemma. You do *not* have to choose between reinventing an Erlang-term
schema in msgpack and switching to distribution for native `eetf`: have the BEAM
run `term_to_binary/1` and ship the bytes as a msgpack binary field, then decode
Rust-side with the `eetf` crate. That's `eetf`'s native fidelity — the exact thing
distribution sells — carried over the transport you already own, with no
reinvented schema, no `AP-03` security surface, and no dist-version handshake.
`term_to_binary`/`binary_to_term` is a few lossless lines on the BEAM side. So the
spike to run before committing isn't "msgpack vs distribution for fidelity" (EETF
settles that); it's the small, bounded one of pinning the term-format version and
making the structured payload opt-in via `describe` so the string-wanting clients
(TypeScript, Emacs) are unaffected. See the architecture review §4 and M2 for the
full treatment.

## 6. Bottom line for xrepl

- **reedline** covers xrepl's entire line-editing wishlist (completion,
  multiline-validation, history, highlighting) and replaces the hand-rolled
  `read-multiline` and edlin-expand completion with a far richer, maintained
  implementation. Its `with_break_signal` is the hook that lets BEAM-side events
  interrupt the prompt.
- **ratatui** + **ratatui-image** delivers the Reveal-like graphics and rich
  inspectors the xrepl design docs spent three documents wishing for — and which
  the LFE `xrepl-term` work is currently reimplementing by hand in escape codes.
- **The architecture must choose a terminal-ownership model up front** (Pattern A
  is the proven, lowest-risk choice and matches nushell). That choice is the
  spine of the next document.
- **The BEAM bridge is real and has prior art** (`erldash`), with one thing to
  verify (OTP-30 distribution handshake) and a safe fallback (the existing
  msgpack socket protocol).
