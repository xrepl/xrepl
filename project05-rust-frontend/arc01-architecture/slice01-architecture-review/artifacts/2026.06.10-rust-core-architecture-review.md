## 0. The thesis, stated plainly

xrepl already contains, in working LFE, the *hard BEAM-side half* of what a great
LFE REPL needs: session isolation under supervision, an evaluator that survives
its own crashes, a transport-agnostic dispatcher, a multi-op protocol, and a
mature protocol library with a TypeScript client already speaking it. What it
*reimplements badly* — line editing, completion, multiline detection, terminal
graphics, and (eventually) the Reveal-like visual surface — is exactly what
reedline + ratatui do superbly in Rust.

So the move is not "rewrite xrepl in Rust." It is **invert the front-end**: let a
Rust core own the terminal and the human, keep the BEAM as the language runtime
and the supervision substrate, and connect them over a protocol xrepl already
has. The BEAM keeps doing what only the BEAM can (run and supervise LFE, hot
code, distribution); Rust does what the terminal ecosystem now does best.

This also resolves the typed-LFE REPL question the parallel thread is chewing on:
**the Rust core is the natural home for the typed checker** (which is already
Rust), so `.lfet` forms can be lowered to LFE *in the front-end* before they ever
reach the BEAM evaluator. The REPL becomes the place where typed and untyped LFE
meet — type-check in Rust, evaluate in BEAM.

## 1. What to keep, what to retire, what to build

A re-platform is only worth it if it *deletes* work, not just relocates it. From
the audit and deep-dive:

**Keep (the BEAM-side assets that earn their place):**

- `xrepl-session` / `xrepl-session-sup` / `xrepl-session-manager` — session
  isolation + supervision. This is the crown jewel; nothing in Rust replaces it.
- `xrepl-eval` + the session-evaluator split — evaluation that's isolated from
  the session loop. (Fix L-13/L-14 first: one boundary, structured errors, an OTP
  behaviour under the evaluator.)
- `xrepl-store` — session registry/persistence (after fixing L-04 orphan-cleanup
  and L-15 read-serialisation; and L-03 atom minting).
- `xrepl_protocol` (the extracted msgpack protocol library) — this is the
  contract the Rust core will speak. It already has a TypeScript client, which is
  *proof the protocol is genuinely polyglot-ready*.
- The op set (`eval`, `clone`, `close`, `ls_sessions`, `describe`, `ping`,
  `load_file`, `upload_history`) — extend, don't replace.

**Retire (let the Rust core subsume these):**

- The LFE line-editing/IO path: `xrepl-io` (`read-multiline`), the
  `lfe_edlin_expand` completion hook, the readline init. → reedline.
- `xrepl-term` graphics (iTerm2/Kitty/sixel escape generation in LFE). →
  `ratatui-image`.
- The bash launcher's four-mode dispatch (`bin/xrepl`) and the
  `xrepl-client`/`xrepl-client-shell` LFE client. → the Rust binary *is* the
  client; the BEAM only ever runs in server/embedded mode.
- The vestigial `lfe_xrepl.erl` shell engine (audit L-18) and the unused
  transport behaviour trio (L-11) — dead before the move; gone after.

**Build (new, in Rust):**

- The terminal front-end (reedline prompt + ratatui views), terminal ownership
  per the model chosen in §3.
- The protocol client (msgpack over UDS/TCP, or distribution — §4).
- The typed-LFE lowering stage (the existing Rust checker, wired as a pre-eval
  pass — §5).
- A small supervisor that owns the BEAM child process lifecycle from Rust (§2).

## 2. The shape: who owns whom

Two processes, one of them supervising the other's *OS process*:

```
┌──────────────────────────────────────────────┐
│  xrepl (Rust binary) — owns the terminal       │
│                                                │
│  ┌──────────┐   ┌───────────┐   ┌───────────┐  │
│  │ reedline │   │  ratatui  │   │  typed    │  │
│  │ (prompt, │   │ (views,   │   │  checker  │  │
│  │  compl., │   │  images,  │   │ (.lfet →  │  │
│  │  hist.)  │   │  inspect) │   │   .lfe)   │  │
│  └────┬─────┘   └─────┬─────┘   └─────┬─────┘  │
│       └───────── core loop ───────────┘        │
│                    │ protocol client           │
└────────────────────┼───────────────────────────┘
                     │  msgpack/UDS  (or Erlang dist)
┌────────────────────┼───────────────────────────┐
│  BEAM node (xrepl OTP app) — owns the language   │
│                    │                            │
│   xrepl-net / dispatcher ── xrepl-session-sup    │
│                               ├── session A      │
│                               │     └ evaluator  │
│                               ├── session B …    │
│   xrepl-store ── xrepl-auth ── (supervision)     │
└──────────────────────────────────────────────────┘
```

**Lifecycle ownership.** The Rust binary starts, then spawns the BEAM node as a
child OS process (or connects to an already-running one for the "attach to a live
system" use case — a major feature, see §6). Rust monitors the child; if the BEAM
dies, Rust reports it cleanly and can restart it (the audit's "let it crash, then
recover" applied across the language boundary). The BEAM, internally, keeps its
own supervision tree for sessions. **Two supervision domains, one boundary** —
and the boundary is the protocol.

This is the inversion of today's design: currently the *BEAM* launches and the
bash script decides client/server; in the new shape the *Rust binary* is the
entry point and the BEAM is a managed runtime. That matches every comparable
tool (a Rust/Go CLI managing a language backend) and it's what makes the single
`xrepl` binary feel native.

## 3. Terminal ownership — the spine decision

From the capability map: reedline and ratatui both want the terminal; there is no
bridge. Three models, in increasing build cost and increasing power.

**Model A — Alternating (reedline default + ratatui on demand). RECOMMENDED.**
reedline owns the prompt in the steady-state loop. Rich views (reveal a value,
browse sessions, show an image, open a live process/ETS dashboard) suspend the
line editor and run a ratatui app, then restore. This is *exactly nushell's
reedline-REPL + `nu-explore`-pager split*, which ships in production today. xrepl
gets best-in-class line editing for free and rich views where they matter,
without solving the concurrency problem.
- *Cost:* lowest. *Risk:* lowest (proven pattern). *Limitation:* no *simultaneous*
  live-region-plus-prompt; rich views are modal.

**Model B — ratatui owns all; prompt is a widget.** One render loop. Prompt via
`ratatui-textarea`/`edtui` inside `Viewport::Inline`, scrollback via
`insert_before`, live regions and prompt coexist. This is the Reveal-like
end-state: a value you evaluated stays live in a pane while you keep typing.
- *Cost:* highest (reimplement completion menus, history-search UI, vi text
  objects that reedline gives free). *Risk:* medium (you own more). *Payoff:* the
  most ambitious, most differentiated UX.

**Model C — reedline + static ratatui output.** reedline for input; structured
*output* (tables, charts) rendered by ratatui to a buffer and printed into
scrollback as static content via `insert_before`. Interactive views still need
Model A's hand-off.
- *Cost:* low-medium. *Payoff:* nice output formatting without modal views, but
  nothing live.

**Recommendation: ship Model A, architect so Model B is reachable.** Concretely:
keep the core loop and the protocol client independent of the terminal-ownership
strategy, behind a `Frontend` trait with two implementations down the line. Model
A delivers a delightful REPL fast and de-risks the BEAM bridge; Model B becomes a
later milestone *if* the live-pane Reveal experience proves worth the cost. Don't
build B first — you'd be solving the hardest UI problem before validating the
transport.

## 4. The transport — msgpack-over-UDS vs Erlang distribution

Two ways for Rust to talk to the BEAM. They are not exclusive; pick the default
and keep the other as an escape hatch.

**Option 1 — Keep the existing msgpack protocol (over UDS locally, TCP
remotely). RECOMMENDED default.**
- *For:* it already exists, already works, already has a TypeScript client
  (proven polyglot), and is decoupled from BEAM internals — the Rust core depends
  on a *message contract*, not on Erlang's distribution-protocol version. The
  audit's protocol-layer fixes (L-01/L-02) make it solid. UDS is fast and the
  file-permission auth model is simple and correct for local use.
- *Against:* it's a custom protocol you maintain; structured Erlang terms get
  flattened to msgpack types (you already format values to strings server-side,
  which is lossy for a future "inspect the live term" feature). **But this con is
  cheaply closed** — see the recommendation below: carry EETF *bytes* inside the
  msgpack frame and you get native term fidelity without leaving this transport.
- *Audit debt to clear first:* L-01 (kill the idle keepalive), L-02 (`packet_size`
  cap + `max_connections`), L-03 (no atom minting per session), L-06 (wire or
  drop the security knobs).

**Option 2 — Speak Erlang distribution from Rust (`erl_dist`/`erl_rpc`).**
- *For:* the Rust core becomes a *real node in the cluster*. You get native term
  fidelity (eetf), `rpc`-style calls, and — the big one — the ability to **attach
  to any running BEAM system** and drive it, which is the killer "production
  debugging REPL" feature. `erldash` proves the stack (erl_dist + erl_rpc +
  ratatui).
- *Against:* distribution is a bigger security surface (the audit's `AP-03`
  applies — a connected node can run arbitrary code on its peers; cookie is weak),
  single-maintainer crate, and **must be verified against OTP 30.0-rc0** (the
  mount's version) before you trust the handshake. More moving parts.
- *Use it for:* the "attach to a live node" mode (§6), gated behind explicit
  opt-in and TLS distribution, not the default local REPL.

**Recommendation:** msgpack/UDS is the default and the thing you build first;
distribution is a *second transport* added when the "attach to production"
feature is built, behind the same `Transport` trait. The existing
`xrepl_protocol` library and its TypeScript client are too valuable to abandon —
they make the protocol a genuine ecosystem asset (Emacs, VSCode, and now a Rust
core all speaking one wire format).

**On term fidelity — the false dilemma to avoid.** The "structured terms get
flattened to strings" con looks like it forces a choice between (a) reinventing
an Erlang-term schema in msgpack and (b) switching to distribution for native
`eetf`. It doesn't. The third option is the obvious one once named:
**EETF-in-msgpack** — the BEAM side runs `term_to_binary/1` on the value and ships
the resulting bytes as a msgpack binary field; the Rust side decodes them with the
`eetf` crate. That is `eetf`'s native fidelity (the exact thing distribution sells)
carried over the transport you've *already built and proven polyglot* — no
reinvented schema, no distribution coupling, no `AP-03` security surface, no
OTP-version handshake. `term_to_binary`/`binary_to_term` is a few lines on the
BEAM side and is lossless. **Recommend EETF-in-msgpack as the value-fidelity path**;
keep full distribution reserved for the *attach-to-live-node* capability (§6,
feature 2), which is the one thing it alone provides. This is the cleanest resolution to the
spike flagged in the capability map's §5.2.

## 5. Where typed-LFE fits (the other thread, resolved)

The parallel typed-LFE REPL exploration asks: how do you type-check in a REPL when
the checker is Rust and the compiler can't read `.lfet`? **The Rust core answers
it structurally.** The pipeline at the prompt becomes:

```
user types a form
   │
   ├─ reedline: edit, complete, validate-balance
   │
   ├─ [if typed mode] Rust typed checker:  .lfet form ──► type result
   │        │                                   │
   │        │  type error ──► show in terminal, don't send to BEAM
   │        │  ok ──► lower to plain .lfe form
   │        ▼
   └─ protocol client: send {op:eval, code: <lowered .lfe>} ──► BEAM evaluator
```

This is the cleanest possible answer to the typed-REPL problem: **type-checking
happens in the front-end, in the language it's already written in, before the
BEAM ever sees the code.** The BEAM evaluator stays blissfully untyped — it
receives already-lowered standard LFE. No LFE macro for `.lfet` is needed (the
audit and the typed-project notes confirm the lowering is Rust's job). Type
errors are caught and rendered *without a round-trip to the BEAM*, which is
exactly the fast, teaching-quality diagnostic experience the typed project wants.

This is a strong argument for the whole inversion: **the Rust core is the one
place where the typed checker, the line editor, and the lowering stage naturally
co-locate.** Doing typed-LFE-in-a-REPL well essentially *requires* a Rust
front-end. The two threads are the same project.

*Caveat (named honestly):* this couples the REPL roadmap to the typed checker's
maturity. Keep typed mode behind a flag so the untyped REPL ships independent of
the checker's progress. The `Frontend`/`Transport` traits keep eval working with
or without the typed stage.

## 6. The features this architecture unlocks (why it's worth it)

The inversion isn't just cleaner — it makes several things *possible* that the
current design can't reach:

1. **Reveal-like live inspection** (Model B): evaluate a value, keep it live in a
   ratatui pane, drill into it — the original inspiration. `ratatui-image` +
   custom inspector widgets over `ratatui-core`.
2. **Attach to a running production node** (distribution transport): point xrepl
   at a live BEAM system and get a typed, visual REPL into it — `erldash`-class
   capability with a real language REPL on top.
3. **Inline graphics that actually work**: `ratatui-image`'s sixel/kitty/iTerm2
   support replaces hundreds of lines of hand-rolled escape-code LFE.
4. **One binary, native feel**: Rust owns startup; the BEAM is a managed child;
   no bash-script mode-juggling.
5. **Typed and untyped LFE in one prompt** (§5).
6. **The protocol becomes the ecosystem hub**: Emacs, VSCode, TypeScript, and the
   Rust core all speak `xrepl_protocol` — the Rust front-end is one more client of
   a contract that's now proven across four languages.

## 7. Risks and the honest unknowns

- **Terminal ownership is genuinely hard if you reach for Model B too early.**
  Mitigation: ship Model A; gate B behind a trait. *Named pull: the excitement is
  toward the live-pane Reveal UX — that's the highest-risk piece, so it must not
  be milestone one.* (This is the same enthusiasm-hazard flagged in the typed-REPL
  exploration; it applies here too.)
- **OTP-30 distribution handshake is unverified** against `erl_dist 0.8.0`.
  Mitigation: msgpack default; verify dist against a live OTP-30 node before
  depending on it.
- **`erl_dist` is single-maintainer.** Mitigation: it's an escape-hatch transport,
  not the default; `edp-rs` is a fallback; the msgpack path needs neither.
- **Protocol value-fidelity** *(largely resolved — see §4)*: today the BEAM
  formats values to strings before sending (audit shows `format-value` → string),
  which is lossy for live inspection (feature 1). The fix is **EETF-in-msgpack**:
  ship `term_to_binary/1` bytes as a msgpack binary field, decode with the `eetf`
  crate — native fidelity over the existing transport, no reinvented schema and no
  distribution coupling. It's a small, additive protocol extension; the only real
  work is making it *opt-in* via the `describe` op's capability negotiation (so the
  TypeScript/Emacs clients, which want strings, keep getting strings) and pinning
  the term-format version both sides assume. Low residual risk, but it's a real
  schema decision — don't let it slip past M2 unspecified.
- **The audit's eight Highs are on the exact layer the Rust core builds on.** Fix
  L-01..L-06 *before or during* the bridge work, not after — a Rust client against
  the current keepalive bug (L-01) will hit the desync on day one.

## 8. Recommended sequence (milestones, not dates)

1. **M0 — Clear the runway.** Land the audit's protocol-layer fixes (L-01, L-02,
   L-03, L-04, L-06) and delete the vestigial surface (L-11, L-18). Re-enable
   xref/dialyzer + a protocol round-trip test suite (L-07). *The Rust work should
   start against a sound protocol, not a buggy one.*
2. **M1 — Rust core, Model A, the existing msgpack protocol over UDS.** reedline
   prompt + a client for `xrepl_protocol` (the already-built, already-polyglot
   wire format — *reuse it, don't invent a transport*) + BEAM-as-child lifecycle.
   Reach parity with today's local REPL: eval, history, completion, multiline.
   This validates the whole inversion with the lowest-risk transport and UI model,
   and on day one the Rust core joins the TypeScript client as a second proven
   consumer of the same contract.
3. **M2 — ratatui views + EETF-in-msgpack term fidelity.** Session browser, value
   pretty-views, `ratatui-image` inline graphics — *and* the structured-term
   encoding that makes real inspection possible: extend the existing msgpack
   protocol to carry `term_to_binary/1` bytes (decoded Rust-side with `eetf`),
   opt-in via the `describe` op. **Recommended explicitly over both alternatives**:
   over a bespoke msgpack term schema (which would reinvent `eetf`), and over
   reaching for distribution just to get native terms (which buys fidelity at the
   cost of coupling, security surface, and an unverified OTP-30 handshake).
   Fidelity arrives on the transport you already own.
4. **M3 — Typed mode.** Wire the Rust typed checker as the pre-eval lowering stage
   (§5), behind a flag. The two threads converge here.
5. **M4 — Distribution transport + attach-to-live-node.** Second `Transport` impl
   via `erl_dist`/`erl_rpc`, TLS-gated, after verifying the OTP-30 handshake. Note
   the *only* reason this milestone exists is the attach-to-a-running-foreign-node
   capability — by M2 the msgpack path already has native term fidelity, so
   distribution is no longer needed for inspection, only for reaching nodes the
   Rust core didn't spawn.
6. **M5 (optional) — Model B live panes.** The Reveal end-state, *if* M2 shows the
   appetite is there. Highest cost, highest payoff, deliberately last.

The ordering is chosen so each milestone de-risks the next and so the
excitement-heavy, highest-risk piece (live panes) comes after the fundamentals
are proven — not before. Note the deliberate consequence: by keeping fidelity on
the msgpack path (M2), the distribution work (M4) is demoted from "needed for the
good UX" to "needed only for one specific feature" — which is exactly where a
single-maintainer, security-heavy, version-coupled dependency should sit.

---

## 9. One-line summary

**Invert xrepl: a Rust core (reedline + ratatui + the typed checker) owns the
terminal and the human; the BEAM (xrepl's existing supervised session/eval
services) owns the language; they meet over the protocol xrepl already
built — start with Model A over msgpack/UDS, and let the live-pane Reveal
experience and production-node attach be the rewards you earn, not the risks you
lead with.**
