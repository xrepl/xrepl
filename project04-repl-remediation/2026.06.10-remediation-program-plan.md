# xrepl Remediation & Re-platform — Program Plan

**Date:** 2026.06.10
**Framework:** house collaboration-framework (AI Engineering Methodology v1.2).
Vocabulary is load-bearing: **Project → Arc → Slice → Step**, with *iteration*
reserved for the fix-loop on an in-progress slice. Slices are sized to fit one CC
context with iteration headroom; ledger discipline (CC implements / CDC verifies,
grep-verifiable rows, five-iteration cap) attaches per slice.
**Source of truth for the work:** `2026.06.10-audit-results-lfe.md` (21 findings,
L-01 … L-21) and `2026.06.10-rust-core-architecture-review.md` (the inversion,
milestones M0 … M5).
**Status:** SDLC steps 2–4 (project definition, design commitments, arc/slice
breakdown). Per-slice implementation plans (step 5) and ledgers are written *as
each slice is picked up*, not up front — the immediate ones are seeded in the
per-arc plans under `docs/design/0.1.0/arc4-green-baseline/` and
`docs/design/0.1.0/arc5-critical-correctness/`.

---

## 1. Project definition

**What we are doing.** Remediating the audit findings and then re-platforming
xrepl onto a Rust core, across two releases with two distinct characters:

- **0.1.0 (branch `release/0.1.x`)** — *stabilise and ship small.* Get the branch
  to a known-good working state, fix a deliberately **limited** set of critical
  correctness bugs that make the shipped REPL wrong or lossy in normal use, sort
  the design-doc archaeology, then tag 0.1.0.
- **0.2.0 (branch `release/0.2.x`)** — *remediate heavy, then invert.* Land the
  remaining (structural) audit items, then begin the architectural inversion (Rust
  core owning the terminal; BEAM owning the language).

**What we are explicitly NOT doing.**

- Not fixing every audit finding before 0.1.0. The 0.1.0 cut is intentionally
  small (see §4, Arc 05). Everything else is *disclosed-deferred* to 0.2.x, not
  dropped.
- Not landing the full Rust inversion in 0.2.0. The inversion spans the arch
  review's M1–M5; 0.2.0 lands at most the foundation (see §6 honesty note).
- Not touching the sibling packages (`protocol/`, `term/`, `typescript-xrepl/`,
  etc.) in this program except where the `xrepl` app depends on them. They have
  their own audit surface and their own releases.

**Smallest complete thing for 0.1.0:** a local stdio REPL that compiles, tests
green, runs, doesn't leak or clobber state in multi-session use, and whose
advertised network mode doesn't desync after 30s. That is the 0.1.0 definition of
done (§4).

**Branch reality (verified 2026.06.10):** `release/0.1.x` exists off `main`; tags
`0.0.0` and `0.1.0` are present; HEAD is `dfab3a0` ("dropping back down to 0.1.0
for a bit"). Untracked in the tree:
`COMMIT_MSG.txt`, `test_quit.lfe`, `tmp/`, an untracked design doc
(`xrepl-protocol-impl-master-plan.md`), and a gitignored `erl_crash.dump`. CI has
xref + dialyzer commented out and `min_coverage=0`.

Sizing note (per the methodology's "sizing is a judgment call"): the Arc 05
slices are deliberately one-finding-each because each is small and independently
shippable/revertable — the right grain for a release where *limited and correct*
beats *bundled*. Arc 06 slices pair findings that touch the same code (L-13+L-14
both in the evaluator; L-12+L-19 both in the local REPL loop; the small grab-bag
in Arc 06 slice6) so each slice is a coherent end-to-end diff, not a scatter. Final
slice boundaries are confirmed when each slice's implementation plan is written —
"if it won't fit one context, it was two slices."

## 4. Release 0.1.0 — definition of done

0.1.0 is done when **all** of:

1. `release/0.1.x` compiles clean and `rebar3 as test lfe ltest` is green
   (Arc 04).
2. The tree is clean: no `erl_crash.dump`, no `test_quit.lfe`/`tmp/`/scratch;
   `xrepl-protocol-impl-master-plan.md` either tracked or removed (Arc 04).
3. Completed design docs are moved to `docs/design/0.1.0/`; forward-looking docs
   remain in `docs/design/` (Arc 04, `slice2`).
4. The four (or five, §5) Arc 05 critical fixes are landed, each with a closed
   ledger and CDC verification.
5. README/`bin/xrepl` claims match reality for 0.1.0 — in particular, network
   mode either works (L-01 fixed) or is labelled experimental. *(Doc-truth check;
   small, folded into Arc 05 `slice1`.)*

Then Duncan re-tags `0.1.0`.

The detailed per-slice scope and ledger-seed criteria live in the per-arc plans:
`docs/design/0.1.0/arc4-green-baseline/arc-plan.md` and
`docs/design/0.1.0/arc5-critical-correctness/arc-plan.md`. The first slice
(Arc 04 `slice1`) is fully worked at
`docs/design/0.1.0/arc4-green-baseline/slice1/` (slice-doc, ledger, cc-prompt,
closing-report, cdc-verification).

## 5. The one open decision — L-02 in 0.1.0 or 0.2.x?

**Recommendation: include L-02 in 0.1.0 as Arc 05 `slice5`.** It's a High (unbounded
pre-auth intake — a `{packet,4}` socket with no `packet_size` cap lets one
connection make the driver buffer ~4 GiB), and the fix is near-free: add
`{packet_size, N}` to the socket opts and pass `max_connections` into the Ranch
`transport_opts`. The reason it's flagged as a *swing* rather than a default-yes:
unlike L-01/L-04/L-05/L-09 it does **not** affect the local default (network is
off by default; the DoS needs an exposed TCP listener), so a strict "only fix what
breaks normal local use" reading would defer it. Given it's a High and ~one diff,
my recommendation is to take the cheap safety win now.

**This is Duncan's call** — it's a scope decision on his release, and either
answer is defensible. The plan is written so Arc 05 `slice5` can be included or moved to
Arc 06 without disturbing the other slices. Default assumption unless he says
otherwise: **included.**

(Its sibling DoS, L-03 atom minting, is *not* a swing — it genuinely needs the
session-registry refactor and stays in Arc 06.)

## 6. Honesty note on 0.2.0 scope

The architecture review lays out the inversion as milestones M1 (Rust core, Model
A, msgpack/UDS) through M5 (Model B live panes). **That is more than one minor
release.** Writing to the floor, not the ceiling:

- **Arc 06 == the arch review's M0** ("clear the runway"). It is real, bounded,
  and the prerequisite for any Rust work. 0.2.0 can confidently *contain* Arc 06.
- **Arc 07 (the inversion) most likely lands only its foundation in 0.2.0** —
  realistically M1 (Rust core reaching local-REPL parity over the existing
  msgpack protocol), possibly the start of M2. M2–M5 (ratatui views, typed mode,
  distribution transport, live panes) span 0.3.x and beyond.
- The Rust-core work needs its own project definition + design doc + arc/slice
  breakdown — it is **not** scoped at slice level in this document. Arc 07 here is
  a placeholder with one decision attached (L-11) and a pointer to the arch
  review. When 0.2.0's Arc 06 closes, we write Arc 07's plan properly.

Stating this now so 0.2.0 isn't quietly expected to deliver the whole Reveal-like
end-state. It delivers the cleaned-up substrate and the first Rust foundation;
the rest is disclosed-deferred to later minors.

## 8. Process commitments for this program

- **One slice, one branch, one ledger.** Each slice lands as a single mergeable
  diff off its release branch, with a grep-verifiable ledger closed before it
  advances. CC implements; CDC (a separate context/subagent) verifies every
  `done` row by re-running its Verify command.
- **Branch naming: `arcN/sliceM-<work-slug>`** (e.g.
  `arc5/slice1-keepalive-desync`). Adopted 2026.06.11, replacing the
  `slice/N.N-slug` form, which carried no arc context. A branch name must
  identify its arc, its slice, and its work without consulting a plan doc.
  Existing local branches renamed host-side (sandboxed git cannot
  complete ref mutations).
- **Audit findings are the Origin column.** Every ledger row traces to an L-NN or
  to a def-of-done item here, so spec-keeping is mechanical: diff delivered rows
  against §2.
- **Five-iteration cap per slice.** Hitting it means the slice was mis-sized —
  re-cut, don't grind.
- **Forever-homes later.** Per Duncan's instruction, all planning docs live flat
  in `xrepl/xrepl/workbench/` for now. Their methodology-default home would be
  `docs/design-v0.1.0/arcNN-<slug>/sliceNN-<slug>/{slice-doc,ledger,cc-prompt,
  closing-report,cdc-verification}.md`; relocation is a later, mechanical move.
