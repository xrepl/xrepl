# xrepl Code Audit — BEAM (LFE + Erlang)

**Date:** 2026.06.10 · **Contract:** `erlang-guidelines` (anti-patterns chapter
as the canonical hunt list) · **Scope:** all of `src/` (27 LFE modules +
`lfe_xrepl.erl`), `test/` (4 suites), and `bin/xrepl`. Diagnosis only — no code
modified.

## Executive summary

xrepl is a genuinely ambitious, well-structured experimental REPL: the
supervision tree is clean and idiomatic, secrets use `crypto:strong_rand_bytes`,
token comparison is constant-time, history writes are atomic, and the
session-evaluator split correctly isolates a long or crashing evaluation from the
session's own gen_server. The dominant cluster of issues is **not** in the
local-REPL core (Phases 1–2, which are solid) but in the **network/protocol layer
(Phase 3)** — which is precisely the surface the Rust-core plan intends to build
on. That layer carries every High-severity correctness bug, is essentially
untested, and advertises security controls it does not implement. A secondary
cluster is **vestigial code**: `lfe_xrepl.erl` is a 1182-line copy of the LFE
shell of which only the command functions are live, and three modules
(`xrepl-output`, `xrepl-transport`, `xrepl-transport-stdio`) appear orphaned from
the live dispatch path. The architecture doc was present, current, and used.

Severity tally: **8 High, 11 Medium, 6 Low, 0 Blocker.** Nothing here is
unrecoverable; several Highs are one-line or one-function fixes. The reason none
is a Blocker is that the network modes are opt-in (`network_enabled = false` by
default), so the shipped default — the local stdio REPL — does not hit them.

## Correctness / soundness

### L-01 · Idle keepalive desynchronises the request/response protocol
**Severity: High**
**Location:** `src/xrepl-tcp-handler.lfe:79-82` (sender);
`src/xrepl-client.lfe:125-140` (victim)

**What's wrong.** The server's `message-loop` has an `(after 30000 …)` clause that
**sends an unsolicited `#m(status ping)` frame** to the client after 30 s of
idle, then re-arms `{active, once}` and loops. The client speaks a strictly
synchronous `send` → `recv` protocol and is not reading between requests.

**Why it's wrong.** After 30 s of think-time at the prompt, the next client
`eval` does `gen_tcp:send` then `gen_tcp:recv`. The first frame waiting in the
socket is the keepalive (`status = ping`), not the eval reply. `xrepl-client:eval`
matches only `#"done"` and `#"error"` (`xrepl-client.lfe:131-136`); a `ping`
status falls through every clause → `case_clause` → the client shell's eval
crashes ("Recovering…"), and every subsequent reply is now off-by-one. This is a
guaranteed failure on any session left idle for half a minute — the normal case
for an interactive REPL.

**Fix.** A REPL connection does not need application-level keepalives at all (TCP
keepalive or the OS handles dead-peer detection). Delete the `after` clause, or —
if liveness pings are wanted — make them a no-op that does not write to the
socket, or move to a framed protocol where the client demultiplexes by message
`id` and ignores unsolicited `ping`s. Given the Rust-core direction, the cleanest
resolution is: the protocol is request/response only; liveness is the client's
job via an explicit `(ping)`.

### L-02 · `{packet, 4}` intake with no `packet_size` bound (pre-auth memory DoS)
**Severity: High**
**Location:** `src/xrepl-tcp-handler.lfe:36-38`

**What's wrong.** The socket is set to `{packet, 4}` with no `{packet_size, N}`
cap. The 4-byte big-endian length prefix is attacker-controlled and unbounded
*before* authentication runs.

**Why it's wrong.** A single connection sending the four bytes `FF FF FF FF`
makes the inet driver attempt to buffer ~4 GiB for one "message" before it ever
reaches `handle-data`/`authenticate-message`. No auth is required to trigger it,
and `max_connections` is not enforced (see L-06), so this is a trivial unauth
node-OOM. (`AP-04`, mailbox/intake overload, applied at the driver layer.)

**Fix.** Set a sane cap in the socket opts: `{packet_size, 1048576}` (or whatever
the largest legitimate eval payload is), and reject oversized frames. Wire the
already-declared `max_connections` into the Ranch `transport_opts`
(`{max_connections, N}`). Both belong in `xrepl-tcp-handler.lfe:36` and
`xrepl-net-sup.lfe:47`.

### L-03 · Unbounded atom minting via `clone` / session creation (post-auth DoS)
**Severity: High**
**Location:** `src/xrepl-session.lfe:103-105`, `src/xrepl-store.lfe:437-441`,
`src/xrepl-history.lfe:28-30` (three call sites, one root cause)

**What's wrong.** Each session converts its id into atoms:
`binary_to_atom(list_to_binary("xrepl-session-" ++ session-id), utf8)` for the
process name, and `"xrepl_history_" ++ session-id` for the ETS table name. A
connected client can create sessions without bound via the `clone` op
(`xrepl-dispatcher.lfe:134-147`).

**Why it's wrong.** Atoms are interned and never garbage-collected (~1M hard
limit). Every `clone` mints at least two permanent atoms; a client looping on
`clone` exhausts the atom table and crashes the node (`AP-02`). UNIX-socket
clients are pre-authenticated, so on a shared host this is reachable by any local
user who can reach the socket.

**Fix.** Stop deriving registered names from the id. Register session processes
through a `gen_server`-backed registry keyed by the binary id (an ETS map from
binary-id → pid), or use `{via, Module, Name}` with a registry like `gproc`/a
local ETS via-module, so no atom is created per session. The history table can be
a single shared `bag`/`ordered_set` keyed by `{session-id, seq}` instead of one
named table per session (which also fixes L-04's table leak). Cap concurrent
sessions per connection regardless.

### L-04 · Expired-session cleanup orphans the process and leaks its ETS table
**Severity: High**
**Location:** `src/xrepl-store.lfe:443-472` (`do-cleanup-expired-sessions`)

**What's wrong.** When a session times out, the cleanup deletes the **store entry**
but, for a session whose process is still alive, it only *logs* "still running"
(`xrepl-store.lfe:466-468`) and then deletes the ETS row. It never stops the
session process.

**Why it's wrong.** After cleanup the system is in an inconsistent state:
`xrepl-session-manager:is-active?` still returns `true` (the process is
registered and `whereis` finds it), but `xrepl-store:get-session` returns
`not-found`. Any code that checks the store then the registry (e.g.
`enrich-session-info`, the dispatcher's `get-or-create-session`) sees contradictory
answers. The orphaned session gen_server, its linked evaluator, and — because the
history table is owned by the session process — its `xrepl_history_<id>` ETS
table all leak for the lifetime of the node. This is the classic "delete the
bookkeeping, forget the resource" leak.

**Fix.** Cleanup must go through the lifecycle owner, not reach into ETS and the
registry directly. Have the store ask `xrepl-session-manager:destroy/1` (which
stops the process via `xrepl-session-sup` and then deletes the store row) for each
expired id. Better: the store should not know about session processes at all —
move expiry to the session-manager, which already owns both halves. (This is also
a layering violation: `xrepl-store.lfe:437` duplicates
`xrepl-session:process-name/1` verbatim — one more reason the store is reaching
across a boundary it shouldn't.)

### L-05 · All sessions persist history to the same file; last writer wins
**Severity: High**
**Location:** `src/xrepl-history.lfe:280-306` (`setup-save-on-exit`),
`src/xrepl-history.lfe:66-74` (`default-file`)

**What's wrong.** Every session's `init` calls `setup-save-on-exit`, which spawns
a process that, on exit, saves *that session's* history to
`default-file` = `~/.lfe-xrepl-history`. All sessions share that one path. The
monitor target is the global `user` process, not the session.

**Why it's wrong.** Two problems compound. (1) **Data loss:** N concurrent
sessions all save to one file; the last writer's history overwrites everyone
else's (the atomic temp+rename in `save/2` makes each write self-consistent but
does nothing about cross-session clobber). (2) **Wrong trigger / process leak:**
the saver monitors `user`; in `--server` mode there is no `user` shell, so the
spawned process blocks forever in `receive` — one unkillable, unsupervised
process per session created (`AP-04` mailbox/idle-process accumulation). For
multiple local sessions, the single `user` exit fires *all* their savers at once,
racing on the one file.

**Fix.** Persist per-session history to per-session paths (e.g.
`~/.xrepl/history/<id>` or a single SQLite/DETS file keyed by session), and tie
the save to the *session* process's `terminate/2` (it already traps exits —
`xrepl-session.lfe:113`) rather than a side-spawned monitor of `user`. Delete the
`setup-save-on-exit` spawn entirely; `terminate/2` is the OTP-correct hook.

### L-08 · `binary_to_list` on UTF-8 source loses multibyte characters
**Severity: Medium**
**Location:** `src/xrepl-dispatcher.lfe:326-336` (`binary-to-code`),
`src/xrepl-dispatcher.lfe:230-243` (`get-key` → code), `src/xrepl-client.lfe:127`

**What's wrong.** Code arriving over the wire is a UTF-8 binary; the dispatcher
turns it into a string with `binary_to_list/1`, which yields a list of *bytes*,
not codepoints, before handing it to `lfe_io:read_string`.

**Why it's wrong.** A multibyte identifier or string literal (e.g. a λ, an
accented name, any non-ASCII in a string) becomes a byte sequence the reader will
mis-tokenise or mis-store — mojibake or a parse error for input that is
well-formed UTF-8. The output path is careful (`unicode:characters_to_binary` is
used in `handle-eval`), but the input path is not symmetric. Output uses unicode;
input uses bytes.

**Fix.** Decode with `unicode:characters_to_list(Bin, utf8)` rather than
`binary_to_list/1` wherever wire code is turned into a form to read
(`xrepl-dispatcher.lfe:334`, and the client's pre-encode in `xrepl-client.lfe:127`
already does the right thing on the way out — match it on the way in).

### L-09 · Hex-parseable session *names* are misclassified as IDs
**Severity: Medium**
**Location:** `src/xrepl-session-manager.lfe:357-370` (`is-session-id?`),
`src/xrepl-commands.lfe:239-255` (`resolve-session-id`)

**What's wrong.** Name-or-id resolution decides "is this an id?" by trying
`list_to_integer(Str, 16)`; if it parses as hex, it is treated as an id and the
name lookup is skipped.

**Why it's wrong.** Session ids are 32-char hex, but plenty of *names* are valid
hex too: `"face"`, `"dead"`, `"42"`, `"abc"`, `"cafe"`. Name one of your sessions
`"face"` and `(switch-session "face")` will look for an id `face`, not find your
session, and report "not found" — a confusing foot-gun with no error at creation
time. (`AP-15`, in-band/ambiguous typing: the type of the argument is being
inferred from its content instead of being explicit.)

**Fix.** Distinguish by id *shape*, not hex-parseability: a real id is exactly 32
hex chars. Check `byte_size`/`length =:= 32 andalso all-hex`; anything else is a
name. Or carry an explicit tag (`{id, X}` vs `{name, X}`) from the call site so
the ambiguity never arises.

### L-10 · `xrepl` gen_server traps no exits but handles `'EXIT'` messages
**Severity: Low**
**Location:** `src/xrepl.lfe:64-71`, `src/xrepl.lfe:50-51`

**What's wrong.** The `xrepl` worker's `init/1` does not set
`process_flag(trap_exit, true)` and the process links to nothing, yet
`handle_info` has two `'EXIT'` clauses.

**Why it's wrong.** Those clauses are dead — the process can never receive an
`'EXIT'` signal as a message. The module as a whole is near-vestigial (its only
live calls are `echo/1` and `version/0`); the dead exit-handling advertises a
fault-tolerance behaviour the process doesn't have. Harmless but misleading.

**Fix.** Either make `xrepl` actually supervise/link something and trap exits, or
delete the `'EXIT'` clauses and acknowledge it is a thin façade. Given the
re-platform, this whole module is a candidate for deletion (its API duplicates
`xrepl-vsn` and a trivial echo).

## API design and invariants

### L-06 · Advertised security controls are never wired
**Severity: High**
**Location:** `src/xrepl.app.src:24-27` (declared);
`src/xrepl-net-sup.lfe` and `src/xrepl-tcp-handler.lfe` (never read)

**What's wrong.** `xrepl.app.src` declares `{require_auth, true}`,
`{rate_limit, 100}`, `{max_connections, 1000}`. Grep finds no reader for
`rate_limit` or `max_connections` anywhere; `require_auth` is implicitly bypassed
for UNIX sockets and never consulted as a key.

**Why it's wrong.** A deployment that reads the app env and concludes "rate
limiting on, connections capped at 1000" is wrong on both counts — there is no
rate limiter, and Ranch's default connection cap is whatever Ranch defaults to,
not 1000, because the value is never passed. Config that lies about the security
posture is worse than absent config: it manufactures false confidence. (Pairs
with L-02, which is the concrete hole `max_connections` was supposed to close.)

**Fix.** Either implement and wire each control (pass `max_connections` into the
Ranch `transport_opts` at `xrepl-net-sup.lfe:47`; add a token-bucket limiter in
`xrepl-tcp-handler` keyed per connection; make `require_auth` a real gate that
can refuse UNIX peers too) or remove the keys from `app.src` until they exist. Do
not ship the keys as decoration.

### L-11 · Unused transport/output abstraction layer
**Severity: Medium**
**Location:** `src/xrepl-transport.lfe` (behaviour),
`src/xrepl-transport-stdio.lfe` (impl), `src/xrepl-output.lfe` (`handle-result`)

**What's wrong.** A `xrepl-transport` behaviour and a `xrepl-transport-stdio`
implementation exist, plus a transport-aware `xrepl-output:handle-result/2,3`.
Grep shows no live caller: stdio drives the dispatcher directly
(`xrepl.lfe:221`), the TCP handler calls the dispatcher directly
(`xrepl-tcp-handler.lfe:136`), and output is formatted inline in the dispatcher
and handlers. The behaviour is not declared by anything that's actually used in
the hot path.

**Why it's wrong.** Dead abstraction is a maintenance tax and a trap: a reader
(or a future contributor wiring the Rust core) reasonably assumes transports flow
through `xrepl-transport`, and they don't. It also means the "transport-agnostic"
claim in the docs is aspirational, not enforced by the type/behaviour system.

**Fix.** Either route all transports through the behaviour (so adding the Rust
bridge is "implement `xrepl-transport`") or delete the unused trio and stop
implying an abstraction the dispatcher doesn't honour. For the Rust-core plan the
*former* is attractive — a real transport behaviour is exactly the seam the Rust
front-end plugs into — but then it must become load-bearing, not ornamental.

### L-12 · `handle-form` is a 100-line nested case/try staircase keyed on exit shapes
**Severity: Medium**
**Location:** `src/xrepl.lfe:199-303`

**What's wrong.** The local REPL's `handle-form` threads response handling through
deeply nested `case`s and a `try` whose `catch` clauses pattern-match on tuple
*shapes* of exit reasons (`#(normal ,_)`, `#(noproc ,_)`) to decide whether a
session vanished (`AP-22` staircase; `AP-06`-adjacent exit-string matching).

**Why it's wrong.** Distinguishing "session closed normally" from a real fault by
reverse-engineering `gen_server:call` exit-reason tuples is fragile: the shape is
an OTP implementation detail, not a contract, and a new OTP can change it. The
function is also hard to follow and hard to test (no test exercises it).

**Fix.** Make session liveness an explicit, checked precondition: before calling,
ask `xrepl-session-manager:is-active?`; on a `noproc`/`normal` exit, treat it
uniformly as "session gone → switch to default" through one helper rather than
four inlined branches. Flatten with `maybe`/helper clauses (`FP-15`). The
network path already returns structured `#m(status …)`; the local path should
consume the *same* structured result rather than catching raw exits.

## Error handling

### L-13 · Double-wrapped eval boundary loses class/stack at the inner layer
**Severity: Medium**
**Location:** `src/xrepl-eval.lfe:58-89` (inner), `src/xrepl-session.lfe:319-334`
(outer)

**What's wrong.** `xrepl-eval:eval-form` wraps evaluation in a `try` that catches
`(tuple class reason stack)` and returns `#(error formatted-string)` — collapsing
the class and stack into a human string. The evaluator-loop that calls it *also*
wraps the call in a `try`. So there are two boundaries; the inner one discards
structure before the outer one can use it.

**Why it's wrong.** A REPL legitimately needs *a* boundary `try` so a user's bad
expression doesn't crash the session (`EH-04`/`FT-04` — this is the right place
for it). But catching at *two* layers, and stringifying class/stack at the inner
one, means the outer handler's `#(eval-error class reason stack)` path
(`xrepl-session.lfe:328`) receives `'error`, a pre-formatted string, and `'()` —
it can never report a throw vs error vs exit distinction, or a real stack. The
information is destroyed one layer too early.

**Fix.** Pick one boundary. Let `eval-form` return either `#(ok value env)` or a
structured `#(error class reason stack)` (no stringifying), and let the single
outer handler format for display. Reserve the human string for the very edge
(`xrepl-io:format-error`), which already exists and does this well.

### L-14 · `evaluator-loop` has no catch-all receive clause
**Severity: Medium**
**Location:** `src/xrepl-session.lfe:311-334`

**What's wrong.** The hand-rolled evaluator loop (`spawn_link` from the session
gen_server) `receive`s exactly one message shape, `#(eval form reply-to)`, with
no catch-all.

**Why it's wrong.** Any other message — a stray `'EXIT'`/`DOWN`, a system
message, a late reply — accumulates in the evaluator's mailbox and is never
drained (`AP-04`/`PC-08`). In normal operation nothing else is sent, so it's
latent, but it is exactly the kind of latent leak that surfaces under the new
distributed/Rust topology where more actors will be messaging these processes.

**Fix.** Add a catch-all clause that drops (and optionally logs at debug) unknown
messages, *or* — better given the re-platform — make the evaluator a proper
`gen_server`/`gen_statem` so `sys` introspection, code change, and unknown-message
draining come for free (`AP-18`/`BEH-01`). The current split (isolating eval from
the session loop) is a *good* instinct; it just wants an OTP behaviour under it.

## Concurrency and runtime safety

### L-15 · Global store gen_server serialises all session reads through one process
**Severity: Medium**
**Location:** `src/xrepl-store.lfe:53-58` (init: `public named_table`),
all `gen_server:call` readers (e.g. `:71-80`, `:104-116`)

**What's wrong.** The ETS table is created `public named_table`, yet every read
(`get-session`, `list-sessions`, `find-sessions`, `get-metadata`, …) goes through
`gen_server:call` to the single store process.

**Why it's wrong.** The table is already `public` — concurrent processes could
read it directly with zero contention. Routing reads through one gen_server
serialises them behind that process's mailbox for no benefit, and makes the store
a throughput chokepoint on the exact path the prompt renderer and dispatcher hit
constantly (`prompt` calls `list` on *every line*; `find-default` does a full
scan per dispatch). Writes need the gen_server for atomicity; reads do not.

**Fix.** Keep writes in the gen_server (for `insert_new`/update atomicity); let
read-only API functions do direct `ets:lookup`/`ets:select` against the public
named table. Replace the `tab2list`-then-filter reads (`find-sessions`,
`list-sessions-detailed`, `do-cleanup-expired-sessions`) with `ets:select` match
specs so filtering happens inside ETS (`AP-11`/`PF-11`).

### L-16 · Socket/token files are chmod-ed after creation (TOCTOU window)
**Severity: Low**
**Location:** `src/xrepl-net-sup.lfe:96-99`, `src/xrepl-auth.lfe:114-121`

**What's wrong.** The UNIX socket and the `auth.token` file are created with
default permissions and then `file:change_mode(..., 384)` (0600) is applied.

**Why it's wrong.** Between creation and chmod there is a window where the socket
/ token is world-accessible. On a shared host a racing local process can connect
to the socket (pre-authed!) or read the token in that window. Small window, but
it's a credential and an authenticated channel.

**Fix.** Create the directory `~/.xrepl` 0700 up front and rely on the directory
permission to gate the contents, and/or set a restrictive `umask` around the
write. For the socket, the parent-directory 0700 is the robust control (socket
file modes are not honoured on all platforms anyway).

## Testing

### L-07 · No static-analysis gate; the protocol layer is untested
**Severity: High**
**Location:** `rebar.config:38-46` (xref/dialyzer commented in `check`),
`.github/workflows/cicd.yml` (xref/dialyzer/coverage commented), `test/` (4
suites only)

**What's wrong.** `rebar3 check` runs compile + eunit + `cover -v
--min_coverage=0`; xref and dialyzer are commented out, in both the alias and CI.
The four test suites cover `config`, `store`, `session-manager`, and
`multi-session`. There are **no** tests for `xrepl-dispatcher`,
`xrepl-tcp-handler`, `xrepl-auth`, `xrepl-client`, `xrepl-history`, `xrepl-eval`,
the msgpack round-trip, or any network path.

**Why it's wrong.** The untested modules are the ones carrying every High finding
above (L-01…L-06). `min_coverage=0` means coverage is reported but never
enforced. For a codebase that is substantially AI-assisted LFE, xref +
dialyzer + the anti-pattern hunt list are the cheapest possible net for exactly
the class of bug this audit found — and they are switched off. The commit history
("Too much LFE for xref checks", `eac9d8f`) shows the gate was removed under
pressure rather than fixed.

**Fix.** Re-enable xref (it will flag the dead modules in L-11 and any
undefined-function calls); add dialyzer with specs on exported functions
(currently absent across the codebase — see L-17); add a protocol round-trip
suite (encode→decode identity, every op in `xrepl-dispatcher`, an auth
accept/reject pair, an idle-keepalive regression for L-01) and a `gen_tcp`-level
integration test that actually connects a client. Set `min_coverage` to a real
floor once the protocol suite exists. This is the single highest-leverage item
in the report: it protects every other fix from regressing.

## Idioms and style

### L-17 · No `-spec`/typespecs on any exported function
**Severity: Medium**
**Location:** whole codebase (e.g. `src/xrepl-session-manager.lfe:6-22` exports 20
functions, zero specs; same pattern everywhere)

**What's wrong.** No module carries dialyzer typespecs on its public surface.

**Why it's wrong.** Without specs, dialyzer (when re-enabled per L-07) has little
to check, and the many `{ok, _} | {error, _}` contracts are documented only in
docstrings — not machine-checked. Several findings here (L-09 ambiguous typing,
L-13 lost error structure) are exactly what specs + dialyzer catch.

**Fix.** Add `-spec` (LFE: the `spec`/`-spec` form, or typespec attributes) to
every exported function, starting with the protocol and session APIs. Pair with
re-enabling dialyzer.

### L-18 · `lfe_xrepl.erl` is ~1000 lines of vestigial shell code
**Severity: Medium**
**Location:** `src/lfe_xrepl.erl` (1182 lines)

**What's wrong.** The file is a copy of LFE's `lfe_shell.erl` (its own header says
so, `:27-30`). xrepl uses only its *command functions* (`c`, `cd`, `ep`, `h`, `i`,
`p`, `pp`, `q`, `m`, …) and the banner helpers. The entire shell engine —
`server/0`, `server_loop/2`, `shell_eval/3`, `read_expression/3`, the slurp
machinery, the eval loop — is dead, because sessions run their own evaluator
(`xrepl-session.lfe`).

**Why it's wrong.** ~800 of 1182 lines are unreachable. It's confusing (two eval
loops, two `update_shell_vars`, two banners), it widens the audit/maintenance
surface, and it carries its own latent issues (e.g. the `m`/`print_compile_time`
format string at `:936` looks malformed — `~.2.0~w`). Before re-platforming, this
is dead weight to shed.

**Fix.** Split the live command functions into a small `xrepl-shell-cmds` module
(or fold into `xrepl-shell-fns`, which already exists for the remote-safe
variants) and delete the vendored shell engine. Keep only what's called. This
also removes the `-import` and the duplicate banner.

### L-19 · Process dictionary holds "current session"
**Severity: Low**
**Location:** `src/xrepl-session-manager.lfe:224,233,248`
(`get/set/clear-current` via `erlang:put`/`get`/`erase`)

**What's wrong.** The "current session" is stored in the calling process's
dictionary (`PC-12`).

**Why it's wrong.** It works for the single-process stdio loop but doesn't
compose: the concept is process-local, so it silently means different things in
the local REPL (pdict) versus the network path (session-id threaded through
`handler-context`). Two mechanisms for one concept is a latent inconsistency,
and pdict state is invisible to `sys`/debugging.

**Fix.** Thread the current session explicitly through the REPL loop's arguments
(it already mostly is — `repl-loop-with-session` carries it) and drop the pdict,
or unify on the `handler-context` record the network path uses. Pick one
representation.

### L-20 · Duplicated helpers across modules
**Severity: Low**
**Location:** `format-form` in both `src/xrepl.lfe:340-348` and
`src/xrepl-session.lfe:340-348`; `process-name`/`session-process-name` in
`src/xrepl-session.lfe:95-105` and `src/xrepl-store.lfe:437-441`; two `ansi-code`
(`xrepl.lfe:434`, `xrepl-client-shell.lfe:324`); two banner readers.

**What's wrong / why.** The same logic is copy-pasted across modules, so a fix in
one (e.g. the L-03 name-derivation change) must be made in several places or drift.

**Fix.** Hoist shared helpers to one module (`xrepl-util` or the relevant owner)
and call it. The `process-name` duplication is the load-bearing one — it's the
seam L-03 and L-04 both touch.

## Things I looked for and did not find (clean)

1. **`binary_to_term/1` on untrusted data (`AP-01`)** — not present. The wire
   protocol uses MessagePack (`xrepl-ptcl-msgpack.lfe`), and `msgpack:unpack`
   keeps map keys as binaries by default, so message *keys* cannot mint atoms.
   (The atom risk that *does* exist, L-03, is from session-id naming, not
   decoding.) Good choice.
2. **Distribution exposed to an untrusted network (`AP-03`)** — TCP defaults to
   `127.0.0.1` and the app logs a warning when bound to `0.0.0.0`
   (`xrepl-app.lfe:60-62`); the README documents SSH tunnelling rather than open
   ports. Correct posture.
3. **Weak token generation / non-constant-time compare** — tokens use
   `crypto:strong_rand_bytes(32)` (`xrepl-auth.lfe:104`) and comparison uses
   `crypto:hash_equals` (`xrepl-auth.lfe:158`). Both correct.
4. **`++` accumulator-on-the-left in hot loops (`AP-09`)** — the recursion-heavy
   paths (history formatting, name columns) prepend-and-reverse or build iolists;
   no quadratic left-`++` accumulator found in a loop.
5. **`if`-staircases and mutable-variable assumptions (`AP-17`/`AP-20`)** — the
   code is idiomatic LFE: guarded clauses and `case`/`cond`, immutable rebinding
   throughout. No `X = X + 1` foot-guns.
6. **Supervisor restart-strategy mistakes (`SUP`)** — the tree is well-formed:
   `one_for_one` at the top with sensible intensity/period, `simple_one_for_one`
   for dynamic sessions with `temporary` children (correct — sessions shouldn't
   auto-restart), `infinity` shutdown for supervisors and bounded shutdown for
   workers. No `permanent` dynamic workers, no missing child specs.
7. **Non-atomic history file writes** — `save/2` writes to a temp file and
   renames (`xrepl-history.lfe:125-132`); each individual write is crash-safe.
   (The cross-session clobber in L-05 is a different problem — the per-write
   atomicity itself is right.)
8. **Self-referential `$ENV` unbounded growth** — explicitly handled: `$ENV` is
   deleted and re-added each update to break the self-reference
   (`xrepl-env.lfe:115-119`), mirroring upstream LFE. Correct.

## Note on method

Findings were derived by working the `erlang-guidelines` anti-pattern hunt list
(`11-anti-patterns.md`) against every source file, then confirming each against
the actual OTP/LFE semantics in the mounted `otp/` (OTP 30.0-rc0) and `lfe/`
trees — e.g. `binary:join/2`'s `since OTP 28.0`, and `lfe_eval`'s `match_symb`
rule that makes an already-bound variable in a `case` pattern an equality match
(relevant to L-09's resolution). No code was run (no `erl` in the sandbox); every
`file:line` was read directly. Severities are commitments, not hedges: the eight
Highs each ship observable misbehaviour to a user of the network modes; the
Mediums will bite the re-platform; the Lows are hygiene and idiom.
